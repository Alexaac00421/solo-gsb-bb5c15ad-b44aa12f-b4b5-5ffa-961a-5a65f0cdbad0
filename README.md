# 实验室样品流转系统

基于 **Python + FastAPI + PostgreSQL** 的实验室样品流转管理 Web 应用，支持样品登记、交接流转、温度监控、自动隔离与完整审计导出。

## 功能

- **样品录入**：样品编号、允许温区（下限/上限）、当前位置。
- **交接流转**：提交含交出人、接收人、目的地的交接单；**接收人确认前样品位置不变**，确认后位置才更新为目的地。
- **温度监控**：记录温度读数；**越界读数使样品立即隔离，且该样品待确认的交接自动失效**。
- **设备故障登记**：登记故障编号、库位、起止时间、原因、操作者；系统按「样品登记位置 + 已确认交接」形成的位置时间段（**均左闭右开**）一次性固定与故障时段、库位有交集的样品，并把其中当前未隔离的样品隔离、使其待确认交接失效；已隔离样品只关联该故障，不重复生成有效隔离。
- **隔离管控**：隔离期间禁止发起转移；仅能通过**注明理由的复核结论**解除隔离（设备故障导致的隔离也不例外）。
- **读数更正**：更正保留原值、理由与操作者（形成更正链），**不会自动解除隔离**。
- **温区调整**：样品允许温区可随实验方案调整；提交时刻生效，保存旧/新温区、理由、操作者与生效时间，并按最新一条读数的最终更正值复核新温区（详见「温区调整」一节）。
- **并发控制**：样品行级锁 + 条件更新（状态/版本号），并发确认或解除隔离时只有基于最新状态的操作生效，冲突返回明确提示。
- **页面呈现**：样品当前状态、流转时间线、温度与更正记录、异常（隔离）记录、审计时间线。
- **审计导出**：单个样品或全部审计记录可导出 CSV（UTF-8，含全部事件明细）。

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

启动后访问：

| 入口 | 地址 |
| --- | --- |
| Web 页面 | http://localhost:8000 |
| 设备故障登记 / 影响清单 | http://localhost:8000/failures |
| 健康检查 | http://localhost:8000/health |
| 全部审计导出 | http://localhost:8000/export.csv |

Compose 包含两个服务：`db`（PostgreSQL 16，含健康检查）与 `web`（FastAPI）。`web` 等待 `db` 就绪后启动，**建表等初始化步骤在应用启动时自动完成**；`SEED_DEMO=true` 时额外写入两条演示样品数据。

停止并清空数据：

```bash
docker compose down -v
```

## 配置项（环境变量）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | `postgresql+psycopg2://lab:labpass@db:5432/labdb`（compose 内） | SQLAlchemy 数据库连接串 |
| `SEED_DEMO` | `true`（compose 内） | 启动时若无数据则写入演示样品 |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `lab` / `labpass` / `labdb` | 数据库账号（compose 的 db 服务） |

端口映射：`8000`（Web）、`5432`（PostgreSQL，便于本地调试，可在 compose 中删除）。

## 设备故障登记（本轮新增用法）

入口：顶部导航「设备故障」→「+ 登记设备故障」（`GET /failures/new`，提交 `POST /failures`）。

填写字段：故障编号、库位、故障开始/结束时间、故障原因、操作者（全部必填）。时间使用页面的 `datetime-local` 控件，按 **UTC** 解释。

业务规则：

- 所有时间段**左闭右开**（`[开始, 结束)`）；开始时间必须早于结束时间，且**故障结束时间不得晚于提交时刻**，否则明确报错。必填字段缺失、时间格式无法解析同样报错。
- 每个样品的位置时间段由「登记位置（从样品登记时刻起）+ 每一次**已确认交接**的确认时刻」切分而成；待确认/已失效交接不改变位置。样品在某库位的时间段与故障 `[start, end)` 在**同一库位**上有交集（`overlap_start < overlap_end`）即进入影响清单。
- 提交后**一次性固定**受影响样品及各自重叠时段（`failure_impacts`，含重叠区间与所处位置时段依据），不随后续位置/状态变化而改变；**没有受影响样品也保存空清单**。
- 对清单中**登记时未隔离**的样品：置为隔离、`version+1`、写入带 `failure_id` 的隔离记录，并把其待确认交接置为 `INVALIDATED`（记录来源故障）。**登记时已隔离**的样品：只关联本故障（影响清单 + `FAULT_LINKED` 审计），**不重复生成有效隔离、不动其交接**。
- **幂等与冲突**：相同故障编号且所有登记字段完全一致的重复提交，直接返回原故障与原影响清单（不重复隔离、不重复失效、不变更版本）；编号相同而字段不一致，返回 **409 冲突提示**，且不改写已有登记。
- **原子性与并发**：登记在单事务内完成。PostgreSQL 下事务第一步对相关表执行 `LOCK TABLE ... IN EXCLUSIVE MODE`（先于任何行锁，避免死锁；允许只读访问），再逐样品 `SELECT ... FOR UPDATE` 基于最新状态计算，与交接确认、录温、样品登记完全串行；SQLite（本地调试）依赖单写库锁与 `busy_timeout`。任何失败整体回滚，**不会留下部分清单或部分状态变更**。
- **解除隔离不变**：故障导致的隔离仍只能在样品详情页走「注明理由的复核结论」流程（带版本号），故障页不提供快捷解除入口。
- 页面可查看：故障列表（`/failures`）、单个故障的影响清单、隔离依据与失效交接（`/failures/{id}`）；样品详情页新增「关联设备故障（隔离依据）」区块，隔离记录也会回链来源故障。审计事件新增 `FAULT_AFFECTED`（故障影响）与 `FAULT_LINKED`（已隔离样品关联），随 CSV 一并导出。
- 对**旧版本数据库**，启动时自动轻量迁移：补齐 `samples.initial_location`、`handovers.failure_id`、`quarantine_records.failure_id` 列并从登记审计回填初始位置，幂等执行，不影响原有启动方式。

## 温区调整（本轮新增用法）

入口：样品详情页「调整允许温区」表单（`POST /samples/{id}/temp-range`）。

填写字段：新下限、新上限、调整理由、操作者姓名（全部必填），表单隐藏携带页面版本号 `expected_version`。**下限必须小于上限**，否则明确报错且不产生任何变更。

业务规则：

- **生效与留痕**：调整以**提交时刻**生效；每次调整保存旧/新温区、理由、操作者与生效时间（`temp_range_adjustments` 表 + `TEMP_RANGE_ADJUSTED` 审计事件），样品 `version+1`。
- **历史不回写**：历史读数原值、更正链、当时的越界判定（`is_out_of_range`）与已形成的隔离记录**一律不回写**；**放宽温区也不自动解除隔离**（仍须走「注明理由的复核结论」流程）。
- **提交时复核**：按**最新一条读数的最终更正值**（有更正取最后一次更正值，否则取原始值）对照新温区判定：
  - **无读数**：只更新温区；
  - **越界且样品未隔离**：立即隔离（生成隔离记录）并使待确认交接失效，与越界录温同规则；
  - **越界但已隔离**：只记录复核结果，不重复隔离、不动交接；
  - **未越界**：仅更新温区并记录复核结果。
- **并发与冲突**：调整事务的第一条语句即执行带版本号的条件 UPDATE（`UPDATE samples ... WHERE version=:expected_version`，版本号 SQL 侧自增）——PostgreSQL 下取得样品行锁、SQLite 下立即取得写库锁，此后的复核读取与全部写入都与录温、更正、交接确认、解除隔离串行化，基于最新状态生效；版本过期返回 **409 冲突提示**（红色消息条），不留下部分变更。为此读数更正现在同样先取样品行锁，保证复核看到的更正链是最新已提交状态。
- **可追溯**：详情页新增「温区调整记录」区块（生效时间、旧/新温区、理由、操作者、复核结果与处置）；审计时间线与 CSV 导出（单样品 `/samples/{id}/export.csv` 与全部 `/export.csv`）均包含 `TEMP_RANGE_ADJUSTED` 事件及复核明细。
- 新表 `temp_range_adjustments` 由启动时的 `create_all` 自动创建，旧库无需手工迁移，原有启动方式不变。

## 历史温控证据报告（本轮新增用法）

入口：样品详情页「历史温控证据报告」区块（`GET /samples/{id}/evidence?start=...&end=...`），报告页内「下载同内容 CSV」按钮（`GET /samples/{id}/evidence.csv`，同样的起止参数）。

页面用两个 `datetime-local` 控件输入起止时间，一律按 **UTC** 解释（也支持 `...Z` 后缀）。

查询规则：

- 时间窗**左闭右开**（`[start, end)`）；起始必须**早于**结束，**结束不得晚于当前时间（UTC）**，否则在页面明确报错（HTTP 400）；样品不存在返回明确错误（HTTP 404）；CSV 下载同样返回对应的文本错误与状态码。
- **窗内读数逐条列出**：读数ID、记录时刻（UTC）、**原始值**、**最终更正值**（无更正即原始值）、**记录时生效的允许温区**及其依据（初始温区 / 温区调整 #id）、**所在库位**及其依据（登记位置 / 已确认交接 #id）、记录人。
  - 温区取**生效时间不晚于读数**的最后一次温区调整；同一生效时刻按调整记录 **ID 较大者优先**；此前为样品初始温区。
  - 库位取**确认时间不晚于读数**的最后一次**已确认交接**的目的地；同一确认时刻按交接记录 **ID 较大者优先**；此前为登记位置。待确认/已失效交接不参与。
  - 越界以**最终更正值**对照记录时生效温区标示（最终值越界），同时保留读数落库时的**原始越界判定**列；两者不一致时分别注明（如「原始判定保留」）。读数按记录时刻、记录 ID 升序。
- **故障相交清单**：另列**已固定**的 `failure_impacts` 中与查询窗相交的条目，展示故障编号、库位、故障时段与**交集时段**（`max(窗起,重叠起) ≤ t < min(窗止,重叠止)`）及登记时是否已隔离。**窗内没有读数也照常展示相交故障，并且该报告永远不输出合规结论**：
  - 最终值存在越界或有相交故障：结论为「不符合」并逐项列出读数/故障；
  - 其余情况（含窗内无读数）：结论为「无法判定合规」，无读数时明确说明不能证明全程受控；读数全部在界且无故障也只表述事实、不作合规证明。
- **一致性**：报告是只读的——PostgreSQL 下在单条 **`REPEATABLE READ` 只读事务**内完成全部读取（读数、更正链、温区调整、交接、故障影响清单共享同一快照），生成期间并发提交的更正或故障登记不会造成报告内部矛盾，也不阻塞业务写入；SQLite（本地调试）在会话开始时显式开启延迟读事务并持有 SHARED 锁（配合 `busy_timeout`），同样以单一数据视图完成读取。报告**不写入任何数据**，不改变隔离、交接与历史审计。
- CSV 与页面**同内容**（UTF-8 BOM；时间统一 UTC ISO）：含报告头（样品/时间窗/生成时刻/结论）、窗内读数表、相交故障表与结论说明；文件名形如 `evidence_<样品编号>_<UTC生成时刻>.csv`。
- 该功能纯查询，无新表、无迁移，**原有启动方式与启动可用性不变**。

## 业务规则与并发设计

- 所有状态变更在单事务内完成；样品状态变更前执行 `SELECT ... FOR UPDATE` 行锁，串行化互斥操作（如「记录越界温度」与「确认交接」）。
- 交接确认使用条件更新 `UPDATE ... WHERE status='PENDING'`；发起交接在落单前以 `UPDATE samples ... WHERE status='ACTIVE'` 守卫，保证并发隔离（越界录温/设备故障）不会在隔离样品上留下待确认交接；解除隔离使用 `WHERE status='QUARANTINED' AND version=:expected_version`（版本号随页面下发）；温区调整把带版本号的条件 UPDATE 作为事务第一条语句（PG 行锁 / SQLite 写库锁一次到位）后生效。并发请求中只有基于最新状态的一个生效，其余收到 **409 冲突提示**（页面以红色消息条展示）。
- 设备故障登记批量影响多个样品，使用表级 `EXCLUSIVE` 锁 + 样品行锁串行化（详见上一节），失败整体回滚。
- 温度读数原始值永不修改；更正写入独立记录（原值、新值、理由、操作者），页面同时展示原始值与当前有效值。
- 每次状态变更写入审计日志（事件类型、操作人、JSON 明细、时间），CSV 导出即完整审计流水。
